# 翻译与审校质量规范

## 1. 先定义翻译策略

根据内容回答：

- 读者是谁，具备什么知识；
- 网站用途是学习、营销、产品操作、参考文档还是叙事体验；
- 应采用何种正式度、叙述人称和专业深度；
- 品牌、人名、机构、标准、命令、API 和缩写如何处理；
- 哪些词必须保留原文，哪些需要首次中英并列；
- 简体中文使用中国大陆、特定行业或用户指定的术语规范。

将结论写入 Brief、Glossary 和 Style Guide，再开始并行翻译。

## 2. 保护程序语义

默认不翻译：

- DOM `id`、`class`、数据键、枚举值和事件名；
- 文件名、路由、URL、查询参数和资源路径；
- 模板占位符、插值表达式、格式化标记和转义序列；
- 代码、命令、变量、函数名和协议字段；
- 数学公式、LaTeX 命令和符号；
- Markdown/HTML/JSON/JS 语法。

不要只看字符串外观。先确定它是用户文案、程序键、数据值还是混合模板。

## 3. 达到高级专业人工翻译水平

### 准确

- 保留事实、限定词、否定、比较、因果、条件和不确定程度；
- 检查数值、单位、日期、公式引用和图号；
- 按领域语境选择术语，不使用词典第一义代替专业判断；
- 不为了“更顺”擅自删减论证或添加原文没有的结论。

### 自然

- 以中文信息结构重写句子，不机械保留英语长句和被动语态；
- 避免重复主语、滥用“进行”“实现”“的”字结构；
- UI 文案短、明确、可操作；正文保持完整论述；
- 保持作者语气，不把克制说明改成营销口号。

### 一致

- 同一概念默认只有一个主译法；
- 多义词在 Glossary 中写明语境分支；
- 标题、按钮、提示和正文中的译法保持协调；
- 变更核心术语时，全站检查受影响位置并记录决定。

## 4. 并行翻译协议

所有主 agent、翻译 subagent 和 reviewer 都必须遵守 `SKILL.md` 的翻译工具原则，不得调用专用机器翻译工具生成初稿、候选译文或审校结果。

每个翻译工作单元必须包含：

- 原文路径与中文路径；
- 独占文件清单；
- 必读的 Brief、Glossary 和 Style Guide；
- 允许修改的范围；
- 受保护内容；
- 进度记录文件；
- 遇到歧义时的上报方式。

翻译 subagent 只做初译：

- 不修改其他工作单元；
- 不重构页面、脚本或样式；
- 不做全站术语替换；
- 不独自改变翻译策略；
- 不反复运行全站测试；
- 将术语疑问、源文错误和动态绑定疑点写入自己的进度记录。

主 agent 承担一个独立翻译工作单元，同时维护全局所有权和未决问题。

## 5. 最终审校方法

### 完整性

扫描残留英文时排除代码、专名、协议字段和必要缩写。检查普通 DOM 扫描看不到的属性、脚本字典、SVG、Canvas 和条件分支。

### 段落级双语对照

逐段回答：

- 信息是否等量；
- 逻辑连接是否准确；
- 指代对象是否清楚；
- 术语是否符合上下文；
- 中文是否能独立成立；
- 是否因分句或合句改变了强调重点。

### 动态语义

文案正确不代表功能正确。对菜单、弹窗、图例和状态提示追踪：

```text
用户动作 → 状态变化 → 数据键或数组索引 → 取值逻辑 → 最终显示
```

同时与原站执行相同操作，核对显示语义，而不是只比较字符串。

### 中文界面

检查：

- 行高、字重、换行和标点挤压；
- 按钮、标签、表头、导航和移动端溢出；
- 图中标签和文字遮挡；
- 中英文、数字、单位和公式之间的空格；
- 屏幕阅读器名称和键盘操作提示。

## 6. Reviewer 分工

大型网站的最终阶段优先使用彼此独立的 reviewer：

- 领域准确性与长文文风；
- 术语一致性与遗漏；
- 动态文案、菜单和弹窗语义；
- 技术资源、布局和运行时完整性。

Reviewer 先列问题和证据，由主 agent 统一修改，避免多人同时重写同一文件。
